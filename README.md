# envelopefile

当前版本提供：

- 命令行版本查询（`--version`）；
- `keygen` 子命令：生成一个 32 字节的二进制密钥文件；
- `encrypt` 子命令：使用已有密钥文件，以 AES-256-GCM 加密单个本地
  文件并保存为二进制封装。

本版本只提供加密（`encrypt`），暂不提供解密子命令；但封装格式完全公开
（见下文“封装文件格式”），可被独立解释与校验。

## 构建与运行

### 依赖

**构建产品本身需要：**

- 支持 **C++20** 的 C++ 编译器（Linux 发行版自带的 g++/clang++、macOS 的
  Xcode Command Line Tools 自带 Apple clang 均可）；
- **CMake 3.20** 或更新版本；
- **OpenSSL 开发文件**（`libcrypto`）。`keygen` 的安全随机字节来自其中的
  `RAND_bytes`，底层由操作系统的安全随机源
  `/dev/urandom`/`getrandom(2)` 提供，不会基于时间、路径或普通伪随机数
  生成。OpenSSL 是产品的必要依赖，缺失时 CMake 配置会直接失败并指出原因。

安装 OpenSSL 开发文件：

```sh
# Debian / Ubuntu
sudo apt install libssl-dev

# Fedora / RHEL
sudo dnf install openssl-devel

# macOS（Homebrew）
brew install openssl
```

**运行自动化回归测试还需要（仅测试用，构建产品不要求）：**

- **Python 3**（测试驱动脚本）；
- 支持链接器 **`--wrap`** 选项的工具链（GNU ld、LLVM lld 等 ELF 链接器，
  Linux/BSD 的默认工具链通常都满足）。

### 默认构建（产品，外加工具链支持时的回归测试）

```sh
cmake -S . -B build
cmake --build build
```

配置时会自动探测当前链接器是否支持 `--wrap`：

- **支持**（Linux 等常见环境的默认工具链）：正式程序 `envelopefile` 与
  故障注入测试程序 `envelopefile_testable` 都会构建，配置摘要会提示
  "fault-injection regression tests enabled"。此时还需要已安装 Python 3
  （见下文“回归测试”）。
- **不支持**（典型情况是 macOS/Xcode 自带的链接器 ld64）：配置与构建
  仍然成功，只生成正式程序 `envelopefile`；配置输出会给出一条明确说明，
  指出故障注入回归在本工具链上**未提供**及原因（链接器不支持
  `--wrap`）。这条说明表示测试**被跳过、并未运行**，不代表回归通过或
  失败，也**不是产品构建失败**：`--version`、`keygen` 与 `encrypt`
  功能完全可用，密钥文件的格式、`0600` 权限保证、拒绝覆盖已有路径等
  行为均不受影响，同时也不需要安装仅供测试驱动使用的 Python 3。

### 只构建产品

如果不需要测试（例如在不支持 `--wrap` 的工具链上，或希望显式关闭测试
构建），配置时关闭 `BUILD_TESTING` 即可，构建过程不会尝试生成或链接任何
故障注入测试程序，也不要求安装 Python 3：

```sh
cmake -S . -B build -DBUILD_TESTING=OFF
cmake --build build
```

### macOS 说明（系统默认工具链）

使用 Xcode Command Line Tools 自带的 Apple clang 与系统链接器即可完成
产品构建，无需更换链接器。Homebrew 的 OpenSSL 不在系统默认搜索路径中，
配置时通过 `OPENSSL_ROOT_DIR` 告知其位置即可：

```sh
brew install openssl
cmake -S . -B build -DOPENSSL_ROOT_DIR="$(brew --prefix openssl)"
cmake --build build
```

系统自带链接器不支持 `--wrap`，因此默认配置下故障注入回归测试不会生成；
配置输出会明确说明这一情况。这不影响 `envelopefile` 的版本查询与密钥
生成功能。需要运行该回归时，请在具备 `--wrap` 能力链接器的环境中构建
（例如 Linux 机器或容器），或配置 `-DBUILD_TESTING=OFF` 只构建产品。

### 查询版本

```sh
./build/envelopefile --version
```

输出：

```text
envelopefile 0.1.0
```

### 生成密钥文件

必须用 `--output` 明确指定保存位置（路径不可为空），生成时不需要口令：

```sh
./build/envelopefile keygen --output ./my-envelope.key
```

成功时退出码为 0，标准输出显示完成提示及保存路径（不会打印密钥内容）：

```text
envelopefile: 32-byte key generated and saved to './my-envelope.key'
```

### 加密单个文件

先用上面的 `keygen` 生成密钥，再用 `encrypt` 指定密钥、原文件与封装
保存位置三个路径：

```sh
./build/envelopefile encrypt \
  --key ./my-envelope.key \
  --input ./document.bin \
  --output ./document.bin.env
```

三个选项分别为：

- `--key <路径>`：已有的密钥文件，其内容必须是**恰好 32 字节的原始
  二进制数据**（即 `keygen` 生成的那份）。程序按原始字节读取，不做任何
  文本解码，长度不是恰好 32 字节（无论更短还是更长）都会失败，也**不会
  自动生成替代密钥**。
- `--input <路径>`：要加密的本地文件。按**原始字节**加密，不做换行符
  转换，也不对零字节等做任何处理；**空文件**同样会生成一个带完整头部与
  认证标签的有效封装。
- `--output <路径>`：封装保存位置。成功时写入一个二进制封装。

成功时退出码为 0，标准输出给出完成提示与保存路径（不会打印密钥或明文
内容）：

```text
envelopefile: file encrypted and envelope saved to './document.bin.env'
```

加密使用 **OpenSSL 的 AES-256-GCM**：每次加密都从安全随机源
（`RAND_bytes`，底层为操作系统的 `/dev/urandom`/`getrandom(2)`）产生
一个全新的 **12 字节 nonce**，并保存完整的 **16 字节认证标签**。封装
本身带有固定标识、版本、算法标识与 nonce，**不依赖文件名或扩展名**解释
内容；用于解释封装的头部信息同样处于 GCM 的认证保护之下，被篡改时认证
失败。

原文件与密钥文件都**只读打开、绝不写入**，因此其内容与权限在加密前后
保持原样。新生成的封装文件以仅当前用户可读写（`0600`）方式创建。

`--output` 指定的路径若**已经存在则一律拒绝**——无论是普通文件、空
文件、目录、符号链接还是指向不存在位置的悬空链接——都不会修改该路径或
其链接目标（悬空链接的目标也不会被创建）。当 `--output` 与 `--input`
或 `--key` 使用同一路径时，同样因该路径已存在而被拒绝，因此不会用封装
覆盖原文件或密钥。若在创建输出文件之后才失败（写入/同步/关闭失败），
程序会关闭并删除本次新建的不完整文件；万一删除本身也失败，最初的失败
原因仍然作为首要错误（退出码 1），并在标准错误追加一条包含路径的警告，
明确提示可能仍留有不完整文件。读入的密钥无论成功还是失败，在操作结束前
都会经 `OPENSSL_cleanse` 从内存清除；任何错误信息与完成提示都只包含
路径与原因，不包含明文或密钥内容。

下列情况以**退出码 1** 在标准错误报告对应原因，且不输出完成提示、不
泄露明文或密钥：密钥无法读取或长度不符、输入读取失败、安全随机源失败，
以及输出保存失败。

## 封装文件格式

封装是一段连续的二进制数据，字节布局固定，可据此被任何独立实现解释。
所有多字节整数在本格式中均为单字节字段，因此不存在字节序（endianness）
问题。字段自上而下依次排列、无分隔符：

| 偏移 | 长度（字节） | 字段 | 取值与编码 |
|---:|---:|---|---|
| 0  | 7  | magic（固定标识） | ASCII 文本 `ENVFILE`（字节 `45 4E 56 46 49 4C 45`） |
| 7  | 1  | version（版本） | 无符号整数，当前为 `1`（单字节 `01`） |
| 8  | 1  | algorithm（算法标识） | 无符号整数，`1` = AES-256-GCM（单字节 `01`） |
| 9  | 12 | nonce | 每次加密由安全随机源新生成的 12 字节原始数据 |
| 21 | N  | ciphertext（密文） | 输入文件的原始字节经 AES-256-GCM 加密的结果；N 等于原文件字节数，空文件时 N=0 |
| 21+N | 16 | tag（认证标签） | 完整的 16 字节 GCM 认证标签 |

即：

```text
+----------+---------+-----------+--------+------------+-----+
| magic(7) | ver(1)  | alg(1)    |nonce(12)| ciphertext |tag16|
+----------+---------+-----------+--------+------------+-----+
            \______________________________________/
                   以上 21 字节头部与密文一并受认证
```

封装总长度为 `21 + N + 16`（空文件时为 37 字节）。

**认证范围（AAD 与密文）**：从第一个 magic 字节到密文最后一个字节为止
的全部数据都参与 GCM 认证——其中前 21 字节头部
（magic/version/algorithm/nonce）作为**附加认证数据（AAD）**，密文作为
被加密并认证的数据，末尾 16 字节即认证标签。因此 magic、版本、算法
标识、nonce 任一被改动，或密文被改动，解密时都会因标签校验失败而被
识别；这也意味着不能绕过头部直接“套用”另一份封装的字段。

**算法参数**：AES-256-GCM，密钥为 32 字节原始数据；nonce/IV 长度为
12 字节；标签长度为 16 字节（128 位）；AAD 为上述 21 字节头部。使用
常见密码库即可独立解密，例如 Python 的 `cryptography`：

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

blob = open("document.bin.env", "rb").read()
assert blob[:7] == b"ENVFILE" and blob[7] == 1 and blob[8] == 1
nonce      = blob[9:21]
ciphertext = blob[21:-16]
tag        = blob[-16:]
key        = open("my-envelope.key", "rb").read()  # 恰好 32 字节
plaintext  = AESGCM(key).decrypt(nonce, ciphertext + tag, blob[:21])
```

## 密钥文件说明

- 文件内容是 **恰好 32 字节的原始二进制数据**，不是可直接阅读的文本，
  没有换行、文件头或任何文本编码（如 Base64）。可以用
  `wc -c < my-envelope.key` 确认大小，用 `xxd my-envelope.key` 查看字节。
- 请妥善保管：**密钥丢失后无法重新生成相同的密钥**，用该密钥加密的数据
  将无法恢复；密钥泄露则加密失去意义。建议将文件保存在访问受控的位置，
  复制备份时同样注意保密。文件权限保证为仅当前用户可读写（`0600`，无执行
  权限，组和其他用户无任何访问权限）：这一保证与进程继承的 umask 无关，
  即使在严格掩码（如 `0400`、`0200`、`0600`）下同样成立，生成后无需再
  手动修改权限即可正常使用。
- 若 `--output` 指定的路径已经存在（无论是普通文件、目录，还是符号链接
  ——包括指向不存在位置的悬空链接），程序都会拒绝生成，不会修改该路径
  或其链接目标，也不会进入删除新文件的处理。父目录不存在、目标不可写入
  同样属于文件创建之前的失败，本次调用不会新建任何文件；安全随机源失败
  发生在打开文件之前，也不会创建输出文件。
- 新文件创建之后，若无法将权限保证为 `0600`（在写入任何密钥字节之前
  停止），或发生写入不完整、同步失败、关闭失败，都会向标准错误报告
  最初的失败原因、以退出码 1 结束且不显示完成提示；程序会关闭本次打开的
  文件并删除本次创建的文件，不影响同目录其他内容，因此正常情况下不会
  留下不完整或权限不符的密钥文件。若删除本次新建文件本身也失败，最初的
  失败原因仍然保留并作为首要错误，标准错误会再追加一条包含目标路径与
  删除失败原因的警告，让用户知道可能仍留有不完整密钥文件；整次调用仍以
  退出码 1 结束。保存结果会区分“新文件已清理”与“清理失败”，不能仅凭
  保存失败就断定文件已被删除。
- 无论保存成功、目标已存在被拒绝，还是创建后失败（含清理失败），内存中
  完整的 32 字节密钥都会在操作结束时清除；成功路径的清除发生在写入、
  同步并关闭文件之后，文件内容就是本次生成的那份密钥。所有错误信息与
  警告都只包含路径与原因，不包含完整或部分密钥内容。

## 命令行用法

```text
Usage:
  envelopefile --version
  envelopefile keygen --output <path>
  envelopefile encrypt --key <path> --input <path> --output <path>
```

缺少 `--output`、路径为空、重复指定 `--output` 或出现不支持的参数时，
报用法错误（退出码 2）且不生成任何文件。

对 `encrypt` 而言，`--key`、`--input`、`--output` 三个选项均为必填，
参数解析是“全有或全无”：缺少任一必填选项、某个选项后缺少路径或路径为
空字符串、任一选项重复指定，或出现未知参数（无论位于哪个位置），都会在
**开始读取密钥或输入、创建输出之前**，以退出码 2 拒绝整次操作，标准
输出为空，标准错误指出具体参数问题并给出 `encrypt` 用法；各选项的先后
顺序可以任意，非空路径中的空格（含首尾空格）属于文件名，不会被裁剪或
拆开。

## 回归测试

`keygen` 的密钥文件创建与失败处理由自动化回归测试保障（`tests/`）。该
回归在链接器支持 `--wrap` 且已安装 Python 3 的环境中**默认启用**（Linux
等常见环境默认构建即包含）；在不支持 `--wrap` 的工具链（如 macOS 系统
链接器）上测试程序不会生成，配置输出会明确说明回归未提供及原因，这不
影响正式程序的功能。以下测试内容仅在测试程序存在时适用，测试不可用的
环境中也可按上文说明正常使用 `--version` 与 `keygen`。

- 参数校验：缺少 `--output`、`--output` 后缺少路径、路径为空字符串、
  重复指定 `--output`（无论两次路径相同还是不同），或出现不支持的
  参数（无论位于输出选项之前还是合法路径之后）时，整次调用以退出码
  2 拒绝——标准输出为空，标准错误说明对应的参数问题并给出 keygen
  用法，不会被误报为文件创建、权限或随机源失败；即使先读到了合法
  路径，也不会在发现后续错误之前保存密钥。指向不存在位置的调用不会
  留下新文件；指向已有文件时其内容与权限保持原样；重复参数涉及两个
  位置时两处都受保护，同目录其他文件不受影响；即使目标已存在会让
  合法调用失败，用法错误仍优先于"目标已存在"被报告。反向对照同样
  保留：非空路径中的空格（含首尾空格）属于文件名，不会被裁剪或拆开，
  仅由空格组成的路径参数不等于空字符串，两者都照常生成密钥；
- 成功路径：恰好 32 字节原始密钥、权限 `0600`（在宽松与严格 umask 下
  均成立）、退出码 0、完成提示包含保存路径、密钥内容不出现在
  stdout/stderr、含空格的路径可正常使用；
- 权限无法保证：无法将新文件权限设置为 `0600` 时以退出码 1 失败、标准
  错误指出目标路径与权限原因、不输出完成提示、本次新建的文件被清理且
  不影响目录中的其他文件；权限设置本身报告成功后，最终核验读不到文件
  权限信息（"无法核验权限"）或读到的实际权限不是恰好 `0600`（仍允许
  组/其他用户访问如 `0644`、或未给当前用户保留完整读写如 `0400`，
  "无法保证 0600"）时同样如此，且程序在写入任何密钥字节之前停止
  （回归通过确认 `write()` 从未到达新文件来证明，而不仅凭目标最终
  不存在），完整 32 字节密钥仍在退出前从内存清除；
- 目标已存在：普通文件、零长度文件、目录、符号链接、悬空符号链接均被
  拒绝，原有内容、权限与链接保持不变，悬空链接的目标不会被创建；
- 创建后故障：写入/同步/关闭失败时返回非零并说明原因，不完整密钥被
  清理且不影响目录中的其他文件；部分写入可由后续写入补齐并成功。清理
  本身失败（删除本次新建文件失败）不会掩盖最初的错误：退出码仍为 1、
  不显示完成提示，标准错误同时保留最初失败原因与一条包含目标路径和
  删除失败原因的警告，不完整文件确实留存，而同目录其他文件不受影响；
  这一结果可与“已清理”区分，目标已存在的创建前拒绝则根本不会进入删除
  处理，也不会出现该警告；
- 安全随机源失败：无论密码库是否提供错误详情，都以退出码 1 结束、
  标准输出为空、标准错误明确说明随机源失败（有详情时保留详情，无详情
  时仍是明确的失败说明，不会被误报为文件写入失败或路径已存在）；即使
  密码库已往密钥缓冲区写入部分数据才报告失败，也不会创建输出文件、
  不会把部分数据当作密钥保存或泄露到 stdout/stderr，同目录其他文件与
  已存在的目标内容及权限保持原样，密钥缓冲区（含已写入的部分数据）
  在退出前仍被清除；
- 密钥内存清除（随机源成功填充之后）：围绕同一份 32 字节密钥覆盖三种
  结束结果——保存成功、目标已存在被拒绝、部分写入后发生不可恢复错误
  ——内存中的完整密钥都在操作结束前经 `OPENSSL_cleanse` 清除。成功路径
  下清除发生在保存完成之后，文件内容就是本次生成的密钥（不是已清除的
  数据，也不是为通过清除检查而重新生成的替代密钥）；写入失败路径清除
  的是完整的 32 字节，而不只是尚未写入的尾部；
- 写入过程：已保存部分字节后写入报告可恢复的中断（`EINTR`）时，从中断
  的偏移继续保存同一份密钥——不丢字节、不重复字节、也不会重新生成另一份
  密钥，多次短写与中断交替时同样完整，且 stderr 不把已恢复的中断当作
  失败；部分写入后发生不可恢复错误，或仍有字节待保存时写入返回零字节
  （无论发生在第一次写入还是已有部分内容之后），都以非零退出并说明写入
  失败、不输出完成提示、不持续重试，并清理本次新建的不完整文件。

测试通过链接器 `--wrap` 从同一份产品源码构建带故障注入的
`envelopefile_testable`（不影响正式二进制），由
`tests/keygen_regression.py` 驱动。除"每次调用最多写入 N 字节/直接失败"
这类固定开关外，故障构建还支持按调用次序编排的写入脚本（正常、短写、
`EINTR` 中断、`EIO` 失败、返回零字节），并记录每次写入的偏移、长度与
结果，据此校验恢复后保存的仍是最初生成的那 32 字节；保存失败后的清理
删除同样可以注入失败（`EF_TEST_FAIL_UNLINK`，仅对本次创建的密钥路径
生效），据此校验最初失败原因与清理警告都会报告、退出码仍为 1、留存文件
不影响同目录其他内容，以及创建前拒绝不会触发删除处理；每次写入还被要求
出自 `RAND_bytes` 填充的那块缓冲区本身，确保写入文件的字节正是随后被
清除的字节，而不是另一份未被清除的副本。权限设置之后的最终核验同样可
注入：可让 `fstat()` 在 `fchmod()` 报告成功后读取失败，或让其成功但回报
任意非 `0600` 权限（如 `0644`、`0400`），据此校验程序不会把"设置报告
成功"当成权限已确认；这些场景下写入跟踪文件根本不会产生，回归据此确认
没有任何密钥字节到达文件。安全随机源的失败
同样可稳定注入：`RAND_bytes` 可被强制返回失败（可选先写入 N 个标记
字节模拟中途故障、可选附带 OpenSSL 错误详情），故障构建同时记录密钥
缓冲区经 `OPENSSL_cleanse` 清除的事件（含清除时已写入的字节数与描述符
状态），据此校验失败路径也会擦除密钥，以及成功路径的清除发生在保存
完成之后。只有清除的指针与长度都和交给 `RAND_bytes` 的缓冲区完全一致
才会被记录，因此跳过清除、只清除部分密钥或清除无关数据都会被回归
识别；产品与回归报告都不会打印完整或部分密钥。
构建后运行（仅在配置摘要显示回归已启用、存在测试程序时有效）：

```sh
ctest --test-dir build --output-on-failure
```

若当前工具链不支持 `--wrap`，`ctest` 会报告 "No tests were found"，这与
配置时的说明一致——是回归未提供，而不是构建失败；请在支持 `--wrap` 的
环境中运行该回归，或使用 `-DBUILD_TESTING=OFF` 只构建产品。
